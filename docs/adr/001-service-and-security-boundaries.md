# ADR-001: Three services, PostgreSQL durability, same-origin browser session

Accepted for implementation, 2026-10-11.

Preserve the existing root Next.js app instead of moving it to apps/web. Java 21 / Spring Boot owns domain resources, authorization, job states, Batch metadata, rendering and audit. Go owns delivery processing and its own persistence. Each service migrates only its own database. No cross-service SQL writes. PostgreSQL is the queue authority; no broker or Redis is required at initial load.

Spring performs OIDC authorization-code login and keeps tokens server-side. Browser receives an HttpOnly, SameSite=Lax session cookie; Secure is mandatory except explicit loopback development configuration. Next rewrites /backend to a fixed trusted core URL and forwards the cookie for server-rendered reads. It is a transport proxy, not a domain BFF. Authenticated data is never cached. Spring CSRF synchronizer token is required for session mutations. Service JWTs require issuer, expiry, audience and allowlisted roles. No CORS allowance is needed. Identity provider must include REPORT_USER/REPORT_ADMIN in the roles claim. Resources belong to immutable subject identifiers, not display names. Initial deployment is single-tenant. Sessions currently reside in memory: restart requires sign-in; multiple web/core instances require sticky routing or persisted sessions before enabling scaling.

Local Keycloak start-dev is a test identity provider, never production configuration. Random local credentials are generated into ignored .env.local. Core database is bound to loopback locally. Production requires TLS, managed secret references, scoped runtime/migration identities, restricted outbound networking and real OIDC configuration.

JRXML is executable trusted code. Only platform-owned templates are enabled first. Upload authoring later requires REPORT_ADMIN plus trusted-author operational review. XML hardening is not a sandbox. Untrusted templates remain disabled until isolated execution with network, filesystem, CPU and memory boundaries exists. No arbitrary template URL fetching. All query templates must bind parameters; reject unsafe $P! substitution for registered JDBC templates.

## Durable execution design

Acceptance atomically inserts immutable resolved configuration, idempotency association and audit event. Resource versions resolve at acceptance. Platform limits override destination defaults, definition defaults and request overrides, in that order of decreasing authority. Secrets are references; secret values resolve just-in-time and never enter job configuration or Batch metadata. Retry of an idempotency key is scoped to subject and fingerprint; same fingerprint returns original resource, different fingerprint returns 409. Initial keys remain reserved for job lifetime; a future documented tombstone/expiry policy must precede deletion.

Each domain job UUID identifies one Batch JobInstance via `jobId`; JobExecution is an execution attempt, StepExecution records a tasklet attempt. Compilation/fill/export are whole tasklets, not resumable pages. Only small identifiers are persisted in execution context. Restart uses the same identifying parameters. User reprocessing creates a new domain job and linked parent UUID, hence a new JobInstance. Completed steps may be reused only when their retained artifact passes integrity validation. Crash recovery must fence stale owners and reconcile Batch execution state before restarting; never just relabel a live worker's execution. Cancellation is cooperative at step boundaries; external uploads already completed are not deleted by cancellation. Deadlines and resource limits must account for non-interruptible Jasper execution.

Core retains artifacts on its own persistent storage for the retry window and exposes an authenticated stream by opaque artifact ID. Go never receives a local path. Multi-instance core requires a shared durable staging object store or routing to durable volume ownership before scale-out. Bytes never enter job JSON or queues. Artifact write uses temporary file + atomic rename before metadata/outbox commit; orphan cleanup is delayed beyond active work windows. Seven-day retention is proposed, not yet enforced.

Java dispatch outbox and Go inbox carry stable task IDs and request fingerprints. Go persists a task before acknowledgement; duplicate same payload is safe, conflicting payload fails. Go controls bounded upload retries and reconciliation. Java controls render retries only. Completion callbacks are durable, authenticated and idempotent. Java aggregates overall outcomes. Neither service may assume a timeout means upload failed.

## Outcome model

Domain: QUEUED, RUNNING, DELIVERING, SUCCEEDED, PARTIAL_SUCCESS, FAILED, CANCELLED. Stage: accepted, compiling, filling, exporting, delivering, complete. Attempt: starting/running/completed/failed/stopped/unknown. Artifact: pending/available/expired/deleted. Delivery: pending/uploading/reconciling/verified/failed/cancelled. Notification: pending/sent/failed. These are separate dimensions.

Required output or required delivery failure => FAILED. All required components succeed and any optional component fails => PARTIAL_SUCCESS. All configured components succeed => SUCCEEDED. No successful required component => FAILED. Verification must precede delivery completion. Notification failure never changes a successful domain outcome. Cancellation wins only if committed before a terminal outcome; it does not revoke already delivered objects. The first slice exposed only one required PDF/destination. Configuration v2 now exposes partial-success outcomes; see ADR-003 for implemented aggregation, lock ordering and mappings.
