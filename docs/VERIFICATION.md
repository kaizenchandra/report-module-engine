## Recovery evidence and limits

The Java recovery test reconstructs interrupted Batch execution metadata in real PostgreSQL, fences the prior epoch, restarts the same JobInstance and avoids rendering again while awaiting delivery. It is not a Java OS-kill test.

Go's recovery test launches a separate test worker process and terminates it with exit code 86 immediately after the provider verifies its upload, before receipt persistence or deferred cleanup. The replacement worker records the interrupted attempt and reconciles the existing S3Mock object using durable PostgreSQL state and retained artifact bytes. It then loses a callback acknowledgement, closes/recreates worker-owned state and replays the durable receipt without another artifact transfer/upload. Final-attempt reconciliation is also exercised. The HTTP core endpoint in this focused Go test is an explicitly labeled test double; browser tests separately cover the real Java–Go integration.

Cloud-control recovery similarly persists the result before a failed acknowledgement and replays it after reconnect without repeating the provider check. Tampered task fingerprints and changed deployment bucket mappings are rejected. Token 401 responses invalidate the cached token for the next request. Scratch and staging cleanup tests preserve referenced, active, recent and unrelated files and symlinks. Process-exit evidence does not certify disk loss, arbitrary partitions, Kubernetes eviction or full disaster recovery.

## Findings resolved during verification
